                         *** ユーザー管理システム (CakePHP to Laravel 移行プロジェクト) ***

1. プロジェクト概要
    - 目標：Laravel のベストプラクティスに基づいた再設計。
    - 重点：より保守性の高いアーキテクチャの構築。

2. アーキテクチャ設計指針
    - 「Thin Controller / Fat Service」の原則を採用し、各コンポーネントの責務を明確に分離しています。
    - Controller: リクエストの受付とレスポンスの返却のみを担当。ビジネスロジックは一切持ちません。
    - Request: バリデーションとデータのクレンジングをカプセル化。Service 層以降では常に信頼可能なデータのみを扱う設計とした。
    - Service: ビジネスロジックの中核。データベース操作や外部連携（CSV出力等）を担当
    - Model: Eloquentを採用し、データ構造 и リレーションシップのみを定義。
        - **Single Responsibility**: 各レイヤーが単一の責務を持つことで、将来的な仕様変更に柔軟に対応できる構成としています。
        - **Eloquent Optimization**:
            - **Scopes**: 姓名連結検索などの複雑なクエリをモデル内にカプセル化し、Serviceレイヤーの可読性と再利用性を向上。
            - **Accessors**: `full_name` などの仮想カラムを定義し、ビューやCSV出力におけるロジックの重複を排除。

3. ディレクトリ構成
   app/
   ├── Http/
   │ ├── Controllers/ # リクエストの制御 (Entry Point)
   │ └── Requests/ # バリデーション (Security Layer)
   ├── Services/ # ビジネスロジック (Worker Layer)
   └── Models/ # データ構造とリレーション (Data Layer)

4. リクエスト処理フロー
    - Request (バリデーション実行)
    - Controller (Serviceメソッドの呼び出し)
    - Service (クエリ構築・ビジネスロジック実行)
    - Model (Eloquent)
    - Response (xxxx.blade.php)

5. 主要機能の実装ポイント
    - ### 5.1
        - 検索ロジックの共通化 - UserSearchService 内に buildSearchQuery メソッドを設け、画面表示用の検索と CSV エクスポート用の検索で同一のクエリ構築ロジックを再利用しています。これにより、検索条件の変更に強い設計にしています。

    - ### 5.2 大容量 CSV エクスポート
        - メモリ効率を考慮し、StreamedResponse と Eloquent の chunk() メソッドを組み合わせて実装しました。
        - 大容量データ出力時でもサーバーメモリの消費を最小限に抑えます。
        - 文字コード：Excelでシームレスに表示できるよう、SJIS-WINに変換されます。
        - 大量データ出力時の安定性を検証するため、17.5万件のレコードを使用してメモリ消費量を計測しました。
          _ **実装手法**: `StreamedResponse` + `Chunk`
          _ **計測結果**:
          _ 開始時メモリ: **18 MB**
          _ ピーク時メモリ: **24 MB**
          _ 実消費量: **わずか 6 MB**
          _ **結論**:
          データを一括で読み込まず逐次処理（Streaming）を行うことで、データ量に依存しない一定のメモリ消費量での出力を実現しました。

    - ### 5.3 論理削除の実装
        - CakePHP での挙動を再現するため、Laravel 標準の SoftDeletes ではなく、専用の t_user_delete テーブルへの記録方式を採用しています。

    - ### 5.4 フロントエンド設計
        - Layouts: layouts.app を基盤とし、全画面で共通の枠組みを維持。- 共通レイアウトファイル (layouts/app.blade.php) を中心に、一貫性のある画面構成を実現しています。
        - Partials: フォーム (\_formFields) や検索パネル (\_searchPanel) を部品化。登録画面と編集画面で同じ入力を使い回すことで、修正漏れを防いでいます。
        - Components: パジネーションなど、システム全体で使い回すUI部品を独立。

6. バリデーション設計
    - CakePHP では Table クラスにバリデーションを記述する傾向がありますが、本プロジェクトでは Laravel の Request を採用しました。これにより、コントローラーが肥大化するのを防ぎ、再利用性とテストのしやすさを向上させています。

7. 結論
    - 本リプレイスでは、CakePHP の既存仕様を尊重しつつ、Laravel の特性を活かした、保守性の高い構成を目指しました。

8. 最適化と投入
    - ### 1.　テストデータ生成
        - システムはFactoryとSeederを使用して生成されます。(TUserFactory.php/TUserBelongsFactory.php)
        - ローカライズ：データは日本語（ja_JP）で生成されます。
        - 整合性：シーケンスを使用することで、IDとメールアドレスの重複を排除します。
        - 効率性：静的パスワードハッシュにより、シード処理が大幅に高速化されます。
    - ### 2. パフォーマンス
        - 開発中、175,000件を超えるレコードを処理する際に発生していた重大なパフォーマンス問題が解決されました。
        - 当初の問題： 深いページ区切りのページにアクセスすると、ブラウザの　Large Contentful Paint（LCP）メトリックが38秒に達しました。
        - 調整
          データベースのチューニング：ソート処理をインデックス付きuser_id（主キー）フィールドに切り替えました。
          フロントエンドの最適化：ページセレクターで16,000を超えるオプション要素が生成されていましたが、これを削除しました。
        - 結果：
          サーバー応答時間が38秒から1.5秒に短縮されました（25倍の高速化）。
          HTMLドキュメントのサイズが3MBから150KBに縮小されました。
